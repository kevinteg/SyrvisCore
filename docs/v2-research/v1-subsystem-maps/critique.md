# Design critique

## Ranked gaps

### 1. No concurrency control in the service plane — **critical**
**Evidence:** `grep -rn flock packages/syrviscore/src` returns nothing (verified). The manager has `locking.hold_lock` (non-blocking `flock` on `<home>/.syrviscore.lock`) but takes it *per primitive*: `download_and_install` releases it between `install_version` and `activate_version`, `cleanup_old_versions` takes it once per version, and `restore_from_backup` (backup.py:413) takes **none** — extraction, symlink switch and manifest write all run unlocked. On the service side there are at minimum five writers to the same tree: the hourly cron `reconcile`, the S99 boot path, seam `apply`/`deploy`, `schedule apply`, and the dashboard in management mode. `services_d` has no lock; `intent.json`, `breakers.json`, `deploy-journal.json` are all unguarded read-modify-write with only per-file `os.replace` atomicity; `deployments._write_record` claims revision numbers with a lock-free `os.link` retry loop. tests-sim: "no cross-process test… the service package contains **no `flock` at all**."
**Consequence:** `instance_bundle._write_declarations` (unlink + atomic write) can race an in-flight reconcile that already loaded declarations — the plan then applies against a set that no longer exists, and the replace-set semantics mean a partially-written set reads as "these services were deleted." Two concurrent `shed` calls lose a row. Two deploys of one service interleave manifest, compose and Traefik writes with no arbiter. This is the highest-severity gap because it is *silent*: every individual write succeeds.
**Closing it:** an instance-level `flock` with a non-blocking acquire and a stated verdict (design/63 D9 already specifies `bringup.lock`), held across plan→apply and across every state-dir mutation; plus a read-modify-write helper for the three `data/state/*.json` stores. This is small code and large behavior change, and it needs a cross-process test, which the suite has never had.

### 2. The safety machinery is written but unwired, and reads as built — **critical**
**Evidence:** verified — `journal_status`, `should_attempt`, `suppressed_by` have **zero non-test callers** in the tree. `breakers.py`'s own docstring: "this module ships the STORE and its arithmetic. The consuming engine… is design/63 M2." `state: "half-open"` is defined, normalized and honored by `suppressed_by` but never written. `healthy` readiness is validated (and a `healthy` edge onto a checkless target is a hard error) but M1 is ordering-only — the journal records `started`, "never `healthy`, because 0.5.16 verifies no health."
**Consequence:** the journal's per-row `breaker:` mirror and the doctrine in design/60 §11 describe damping, half-open probing and page-once semantics that nothing enforces. An operator (or an agent) reading a status surface reasonably concludes retries are bounded; they are not. A declaration can assert `db:healthy` and get ordering only — precisely the "checks that report what they cannot see" failure that `dep:F9` refuses elsewhere in the same module. The `deploy_bundle` journal also *leaks*: `record_event(STARTING)` fires at service_manager.py:3257 and at least six `return False` paths follow (3277, 3291, 3293, 3296, …) before the terminal events at 3442/3467 — every refusal leaves a permanently in-flight run that goes stale at 60 minutes and then annotates every later bring-up.
**Closing it:** either wire M2 (skip/half-open/page engine, ~a week of work plus the daemon question in §Tensions) or *demote the display* — a store with no engine should not render as a breaker anywhere. Plus a `try/finally` around the deploy body so no early return can leak a run.

### 3. The shutdown budget does not fit its transport, and stores are never clamped — **critical (data), unproven**
**Evidence:** `DEFAULT_SHUTDOWN_BUDGET_S = 180`; measured reserve is "store wave 120s + VM ACPI 90s + core 30s = **240s** irreducible"; the rc.d `stop)` case bounds the whole flush at `timeout 150s`. The source says outright: "DSM's rc.d-stop timeout is UNVERIFIED here — a real DSM-reboot test must confirm." Reserve-first clamping deliberately never clamps the store band.
**Consequence:** on a plain DSM reboot a store-heavy instance can be SIGKILLed mid-walk — the exact "postgres force-killed at 5s is a WAL replay or worse" outcome the doctrine exists to prevent. Compounding: `elapsed_s` saturates at `budget_s` on overrun (`_remaining` is floored at 0), so the one number an operator would tune with is the one that cannot report the overrun. And design/28's addendum notes the UPS trigger itself lives in DSM UI toggles no allowlisted verb can read — "until it is, nothing triggers the flush on a real outage."
**Closing it:** measure the DSM rc.d stop window on the box (there is no simulator path — see gap 12), then reconcile the three numbers or move the flush out of `rc.d stop` entirely; fix `elapsed_s`; add a read verb for the DSM UPS toggles so the trigger is observable.

### 4. Backup/DR has drifted behind the storage model — **high**
**Evidence:** verified `_gather_backup_items` (backup.py:156) walks `config/`, the L1 data dirs, `services/`, `compose/`, `data/<svc>`. 0.5.x L2 apps live at `<volume>/<apps-root>/apps/<name>/{data,config,secrets,logs}` (`service_manager._app_home`/`_volume_home`), declarations live in `config/services.d`, and `layer2_services` is derived from a `home/services` directory modern installs may not have. vision-data confirms 15 located services today. design/53 §6.2-2 called it "the one genuine 0.6 platform bug this design surfaces."
**Consequence:** a "full disaster-recovery backup" captures none of the app homes, none of the located `config/`/`secrets/` slots, and — worse — the archive's own metadata does not declare the omission, so the artifact *asserts* completeness. `preupgrade` also writes `backups/upgrade-<ts>/` directories that `list_backups` (globs `*.tar.gz`) ignores and `cleanup_old_backups` never removes: unbounded junk in the DR directory.
**Closing it:** route backup through the same `_app_home`/`_volume_home` resolvers the runtime uses, record `scope` + covered roots in `backup-metadata.json`, extend the `dev-loop` DR job to a *located* service, and teach `list_backups` about the preupgrade directories.

### 5. Auto seam sync fails open on width, and drift is unobservable over the seam — **high (security)**
**Evidence:** `auto_sync_after_activate` runs the newly-activated version's own generator **as root**, and that generator rewrites the sudoers/shim that constrain it (`seam_sync.py:11-14` records the trade honestly: "the trust anchor becomes the release channel plus this root-held policy file — not a human re-provision"). Rolling back below 0.4 raises `SeamSyncError("…artifacts left unchanged")` — the boundary stays **wider** than the running code. `shim_path` in `seam-policy.json` is never cross-checked against the forced command in `authorized_keys`. `syrvisctl seam status` calls `ensure_privileges` and re-execs under sudo, so policy drift is only observable from the break-glass login the seam exists to eliminate. The committed drift artifacts are rendered at the `/volume1` default while the box runs `/volume4` — the drift test proves the generator is stable, not that the deployed policy matches.
**Consequence:** the enforcement boundary can silently exceed the running version's vocabulary, and no seam verb can see it. Secondary: sudoers globs are far looser than the shim (`service task --task * -- *`), so any second key on the operator account without a forced command collapses the boundary to the glob layer; `ensure_config_tree_readable` grants every docker-group member read of L2 declarations; `guard_bulk_degraded` hardcodes `by="cli:force"`, so a seam- or MCP-driven `--force` closes breakers as if a human typed it — exactly the inference `opc:F2` was written to forbid.
**Closing it:** add `seam status --json` as a *read* seam verb (no sudo — it can compare hashes of world-readable renders), cross-check `shim_path` against `authorized_keys` at sync time, refuse to leave artifacts wider than the active version (narrow-or-fail on rollback), and thread `by` through `guard_bulk_degraded`.

### 6. The reader-enumeration gate is prose, and image publishing contradicts itself — **high (coupling/versioning)**
**Evidence:** `depends_on` is *inside* `ALLOWED_TOP_LEVEL_KEYS`, so `tolerant=True` gives the dashboard no protection at all: a stale image's `from_dict` still raises → the file lands in `invalid` → the name is absent from `declared` → `state_of()` returns `"unmanaged"`, "the one state it definitively is not." The gate ("rebuild + repin the dashboard before any edge lands"; "rollback below 0.5.16 forbidden") lives only in `CLAUDE.md`. Meanwhile `.github/workflows/dashboard-image.yml` tags at the **service** version while `test.yml`'s job and `build-dashboard.sh` tag at the **dashboard** version; both fire on merge and both push mutable `:latest`. Precedent: the 0.5.10 image returned an empty L2 list with `error: None`; 0.5.9 emptied it silently via an over-strict home check. Two silent-blindness regressions in three image releases.
**Consequence:** the mitigation for total failure is accidental (the planner's floor check raises if *every* declaration carries an edge); partial adoption gets no protection and produces a confident wall of `unmanaged`.
**Closing it:** a declaration-schema epoch integer written where every reader must read it, an assertion of the reader's epoch in `/api/summary`, deletion of the relic workflow, and a CI tag gate that fails when `DEFAULT_DOCKER_IMAGES["dashboard"].tag != dashboard.__version__` or when an epoch bump ships without a repin.

### 7. Six state stores that can disagree, with no reconciler over them — **high (consistency)**
**Evidence:** symlink vs manifest (resolved: symlink wins, documented). Beyond that: `services.d` vs installed manifests (planner diff) vs `drift.py`'s compose-vs-Docker diff — two independent drift notions that can disagree, with shed filtering bolted on in `verify.py:108` for only one of them. `intent.json` read/write asymmetry (`read_intent` accepts any `service`/`reason`; the next legitimate write raises `IntentError` on the whole document), shed rows never garbage-collected, and a shed row for a deleted declaration still blocks dependants forever via `dependency_blocked`. Deployment records: retention at 50 silently removes rollback targets with no warning, and `_bundle_change_set` is FAIL-CHANGED against the *newest* record. Breakers: unknown `schema_version` → `read_breakers` returns `[]` while `write_breakers` raises, and `_record_deploy_breaker` swallows the raise — counting stops with no operator signal.
**Consequence:** "what is true right now" has no single answer, and each surface derives it differently. This is the structural version of design/61's thesis sentence: "nothing on the box could answer 'what phase is this machine in, and what is actually true right now?'"
**Closing it:** one `syrvis state` verb that reads all stores, reports disagreements as findings, and GCs (expired shed rows, orphaned shed rows, breaker rows for deleted services); make the unknown-schema behavior symmetric and loud.

### 8. The stdin plane is outside the enumerated model — **high (trust boundary)**
**Evidence:** `RemoteRunner.run` pops `_stdin` before argv construction (correct, and well argued), but "stdin writers are script-only, never MCP tools" is enforced by *nobody* — `remote.py` supports `_stdin` generically, so a tool exposing `deploy`/`secret set` is one function away. Shim validation does not see stdin at all; the only bounds are 1 MiB / 64 KiB plus downstream schema. Separately, `privilege.self_elevate` re-execs an argv shape (`sudo SYRVIS_HOME=… <python> <argv>`) that is **not** in the sudoers policy — two coexisting privilege models, one enumerated and one not.
**Consequence:** the seam's central claim ("the enumerated list *is* the security boundary") is true for argv and aspirational for payloads. A future MCP tool that streams a bundle puts secrets in an LLM context with no structural objection.
**Closing it:** a registry flag (`stdin_only=True`) that the MCP tool generator refuses to project, asserted by a test; and either enumerate the self-elevation shape or route local elevation through the wrapper.

### 9. `syrvis setup` — the verb every install runs first — is essentially untested and partly broken — **high (test blind spot)**
**Evidence:** setup.py at **11%** coverage, 5 tests covering only `.env` idempotency. `write_stack_file` keys off `config.get("dashboard_enabled")`, which `prompt_configuration` never sets, so setup cannot enable the dashboard. Non-interactive setup never populates `cloudflare_dns_api_token` or `portainer_password`. With no `stack.yaml`, `infer_stack_from_env()` enables cloudflared and compose emits `TUNNEL_TOKEN=${CLOUDFLARE_TUNNEL_TOKEN}` with no default — an unset token yields a restarting container. Neighbours: `doctor.py` 9%, `update.py` 11%, `privileged_ops.py` 43%, no `test_verify.py` or `test_doctor.py` in a 56-module suite.
**Consequence:** the reproducibility principle ("running `syrvis setup` should result in a fully working system") is asserted by documentation and by nothing else.
**Closing it:** an end-to-end setup test against a `tmp_path` install root with `SimulationOperations`, and a non-interactive setup path with explicit required-input errors.

### 10. Docker is never exercised anywhere in 2,038 gated tests — **high (test blind spot)**
**Evidence:** `_start_service`/`_reload_traefik` stubbed at instance level; `docker_manager` `MagicMock`ed (63%); the dashboard forces a dead `DOCKER_HOST`. Proven consequence class: 0.5.12 read `RestartCount` from `attrs["State"]`, "a location Docker has never populated" — the fake fabricated the field, 1,100 tests passed, flapping detection shipped inert to production.
**Consequence:** the G1 rule rests on an unverified premise — that `up -d --force-recreate` re-bakes env and `compose restart` re-reads a bind-mounted file. Nothing verifies a generated compose is one Docker will accept.
**Closing it:** one containerized integration job (Docker-in-Docker on the runner) exercising generate→up→recreate→restart against a trivial image. It does not need DSM; it needs a daemon.

### 11. The SPK — the only artifact DSM installs — has no CI at all — **high**
**Evidence:** no `build-spk`/`validate-spk` job; no `sh -n`, no shellcheck on `preinst`/`postinst`/`postupgrade`/`start-stop-status`. The error taxonomy (263 gzipped outer tar, 261 missing `start-stop-status`, 313 `scripts` packed as tar, 276 privilege) is guarded by human memory and two shell guards. `preupgrade`, `preuninst`, `postuninst` and `syrviscore-bootstrap.sh` each reimplement home discovery in shell and **none** knows about `<name>_1` collision renames or the configurable apps-root; `preupgrade` still probes a legacy `$VOLUME/docker/syrviscore`. `spk/INFO` reads `version="0.1.21"`.
**Consequence:** the SPK's reliability is a stated DR requirement ("this makes the SPK's reliability a DR requirement, not a convenience") and is the least-gated artifact in the repo. The 2026-08-16 collision hardening reached the Python layer and stopped at the shell boundary.
**Closing it:** a CI job that builds the SPK, runs `validate-spk.sh`, `sh -n` on every script, and asserts the outer tar is uncompressed and `scripts/` is a directory; then port the collision/apps-root logic into a single sourced shell helper.

### 12. The DSM simulator is dead, so every DSM-interaction path is production-tested — **high**
**Evidence:** everything in `tests/dsm-sim/` dates to 2026-07-09 against a 2026-08-17 tree; neither shell test runs in CI; `SimulationOperations.ensure_boot_script` writes a *different* S99 body than production renders; there is no mock for `synocheckshare`, `synoschedtask`, `synowebapi`, `crontab`, `ip`, or `docker`. The advisory `synocheckshare` phase gate is asserted only as a substring ordering — the wait loop never executes.
**Consequence:** the audit's 2026-07 verdict ("the DSM simulation simulates success, not DSM"; "Would the suite have caught the real NAS failures? **No**") is only half-retired. The paths that produced 2026-08-16, 2026-08-10 and 2026-07-30 remain the paths with the least coverage — the rhyme with 2025-12-26 (eight versions in one day) is structural, not stylistic.
**Closing it:** delete the simulator or rebuild it as a transcript fake, and expand the "run the rendered shell" technique (already proven in three modules) to the boot hook's wait loop and the SPK scripts.

### 13. Four writers of the boot artifacts, and a contract integer that no longer means content — **medium/high (lifecycle)**
**Evidence:** `update.py::_regenerate_boot_artifacts`, `version_manager.activate_version → syrvis _regen-boot-hooks`, `syrvis setup`, and `verify --fix`'s `boot_script` action all write S99. `BOOT_HOOK_CONTRACT`/`MIN_BOOT_HOOK_CONTRACT` are hand-duplicated across the package boundary, held by one test — and the `synocheckshare` gate deliberately did not bump it, so the integer now marks *capability*, not currency. `update.py` is a second, stale version manager still registered in `cli.py:111`: it downloads `.spk` assets, builds venvs service-side, has no backup integration, and its `rollback` picks "the first version that isn't current."
**Consequence:** the 0.5.2 root cause ("the DEPLOYED `syrvis-startup.sh` had drifted years behind the code… no validator caught the drift") is structurally still possible from the writer nobody audits.
**Closing it:** delete `update.py`, make `render_boot_script` the single writer behind one verb, and make the contract a rendered-content hash with a separately-declared capability integer.

### 14. Composite operations are not transactional — **medium (architectural)**
**Evidence:** `apply_instance_bundle` writes env → stack → declarations, each atomic, none joint; recovery is documented as "re-run apply." `download_and_install` releases the lock between install and activate. `sync_from_source` installs declarations and unlinks stale ones *before* materializing scripts — a mid-way failure leaves `jobs.d` at the new commit and `jobs/` at the old, and `apply_schedule` then silently unschedules them.
**Consequence:** every crash window has a distinct half-applied state, and none of them is named or detectable.
**Closing it:** a two-phase pattern (stage the whole set beside the live one, swap a directory symlink) for `services.d` and `jobs/`, mirroring the version tree's own stage-then-swap — the pattern already exists three times in this repo.

### 15. Enable-guard and replace-set asymmetries — **medium (safety)**
**Evidence:** `instance_bundle._plan_declarations` enforces `guard_enable_change`; `converge.apply_plan`'s declare path applies only the shed overlay — `stack apply --from` can flip declared-off → declared-on unguarded. Replace-set removal has no guard at all: an accidental omission from a bundle deletes the declaration, the container becomes `unmanaged`, and nothing reports a failure.
**Consequence:** the 2026-08-16 resurrection class is closed on one of two paths.
**Closing it:** move the guard into a single admission function both writers call; add a removal threshold (`--allow-removals N` or a fraction gate) to the replace set.

### 16. MCP adapter has fallen behind its own enforcement boundary — **medium**
**Evidence:** 50 tools against 77 registry commands; `vm_*`, `service shed/unshed/recreate`, `schedule dsm-tasks`, `syrvisctl doctor`, `reconcile_force` are permitted on the key and unreachable as tools. Verified: `_KIND_VALIDATORS` has 16 entries against 18 registry kinds (`git_rev`, `sha256_digest` missing) — `resolve_slot` would raise a bare `KeyError`, escaping `_call`'s `except McpError`; currently latent because no tool uses those kinds. `_parse_ssh_user` matches `Host` lines by exact equality, so a multi-alias/pattern/`Include`/`Match` config yields `ssh_user=None` and the root/admin refusal is silently skipped. `_call` calls `get_context()` outside its `try`, so the most likely first-run failure surfaces as a traceback. Audit lines have no timestamp, rotation, or size bound.
**Closing it:** tests asserting kind-coverage and tool⊆registry, an `ssh -G` based user resolution, and moving `get_context()` inside the funnel.

### 17. Dashboard read-path and presentation gaps — **medium/low**
**Evidence:** `/api/docs` and `/api/openapi.json` are registered by the `FastAPI()` constructor and escape `require_user` (schema only — low). In `both` mode `require_user` checks the OIDC session before the Cloudflare JWT, so a stale cookie outranks a live Access assertion; `SessionMiddleware` sets `https_only=False` unconditionally. With the default `:ro` data mount the image-update cache can never be written, so `/api/summary.image_updates` stays `null` forever. The frontend has no pill for `shed`, `terminal` or `blocked` — all three render as "Unmanaged", reproducing in the UI the exact mislabel the backend comment calls "the one state it definitively is not."
**Closing it:** mount docs behind the router, reverse the auth order, `https_only` from mode, and a frontend state-vocabulary that mirrors design/57 D11's seven words.

### 18. Declarative doctrine with no share verb, no logging key, and prose-only cross-repo gates — **medium**
**Evidence:** `syrvis share declare|list` does not exist; every share is hand-made in the DSM UI — the exact process that armed the collision landmine. `logging:` is deferred to 0.6, so **every container today has unbounded logs**, and all 12 managed jobs discard output. `.data-plane.yaml` is declared by six datasets and written/read by nothing. `docs/design-doc.md` still claims "Version 3.0 / Status: Implemented" while documenting a removed `migrate` verb and a removed symlink; four docs are untouched since 2025-12-26; the wiki still says `depends_on` is rejected.
**Consequence:** doc rot here is not cosmetic — `docs/wiki/07-service-schema-reference.md` omits ~10 of 28 allowed keys, so the schema's *own* published surface understates the trust boundary it defines.
**Closing it:** a doc-conformance lint (allowed keys ↔ reference table; CLI verbs ↔ `cli-syrvis.md`), a `SUPERSEDED` banner on the four stale docs, and a `logging:` key with a default.

## Cross-cutting tensions

**Python 3.8, forever, for DSM parity.** The pin is correct — the code that runs on the NAS is the code that is tested — and it costs more than it looks. Black is pinned repo-wide at 24.8.0 because it is the last release installable on 3.8; CI pins `ubuntu-22.04` because newer runners no longer ship 3.8; the MCP and dashboard need a second interpreter and a second CI job; the three suites cannot be collected in one process; and 91 tests are orphaned partly as fallout of that split. The pin binds until DSM moves or SyrvisCore ships its own interpreter — and shipping an interpreter would break the "SPK is a lightweight bootstrapper" constraint that Error 276 forced in the first place.

**CLI-as-engine vs a daemon.** Every operation is a one-shot process, which is why `is_flapping` is inferred from a single sample ("an engine that has to remember a previous observation to notice a crash loop cannot notice one across a restart of itself"), why a half-open timer cannot exist without polling, why nothing serializes writers, and why design/61 is 1,320 lines of unbuilt Go. The benefit is real and should not be traded away casually: every action is reproducible from a shell, inspectable in files, and cannot be taken hostage by a wedged daemon — and `ssh nas && syrvis …` remains a complete substitute for every adapter. The honest reading is that v1 needs *one* long-lived thing (a lock holder and a timer), not a supervisor.

**Files as the database.** Atomic per-file writes buy crash-safety, human legibility and zero operational dependencies; they cost transactions, cross-file invariants, and indexes. The planner pays two Docker round-trips per declared service on every hourly reconcile of a 39-service fleet. Six stores now hold overlapping truth with no schema between them. Files were the right call; what is missing is the *one* thing a database would have given for free — a serialization point.

**One-shot reconcile vs continuous convergence.** Reconcile is pure, idempotent, cheap to reason about, and the plan/apply split is exemplary. But nothing converges between cron ticks: a service that dies at 12:05 stays dead until 13:00, and with no breaker engine a crash-looping dependency is retried at full rate every hour. The buckets (`disabled`/`shed`/`terminal`/`blocked`) are the right vocabulary for a system that will eventually gate; today they are the right vocabulary for a system that never retries differently.

**Generic platform vs deployment repo.** The discipline is real and rare — `exposure` as declaration, no domains or accounts in code, `shares_registry` reading five keys and ignoring the rest so home-tech can keep richer semantics in the same files. It is what makes the repo open-sourceable. It also exports the hardest problems: share creation belongs to no engine, `make introspect` cannot exist because home-tech has no Makefile, design/50 is 0-of-11 implemented, and the platform cannot enforce its own cross-repo gates (the reader-enumeration rule, the rollback prohibition, the tag gate) because they are properties of two repos and live in prose in one. The split also means SyrvisCore's history is not reconstructible from SyrvisCore: a reader hitting "design/63 D2 as amended, `opc:F10`" has no local referent.

**Refuse-don't-guess.** The strongest cultural rule in the codebase, and it compounds: the floor check, the vanished-home refusal, location and per-volume immutability, the collision precheck, `guard_enable_change`, the manifest parser, the `.env` hazard guard. Each is right. Together they form a growing surface where operations can wedge, and a refusal without an automated remediation is runbook debt. The best of them name the exact recovery command (`sudo mv …`, `ls -d /volume*/syrviscore*`) and delete the destructive advice; the rule should be that *every* refusal does.

**Incident-driven design.** Nearly every constant carries the incident that set it, which yields extraordinary signal per line. It also optimizes for the last failure. The untested classes — concurrency, ENOSPC, truncated writes, a killed process mid-deploy, real Docker semantics — are precisely the ones that have not yet produced an incident, and the suite has ~10 failure injections across 56 modules.

## What v1 got right

**The operator seam is the crown jewel and must survive a rewrite intact.** One registry renders the sudoers policy, the forced-command shim and the provision script, with a committed drift test; the shim re-validates independently (charset whitelist, `wc -l` newline check, `set -f`, exact arity, per-kind predicates, `exec "$@"`); every user positional lands after `--`; each override shape (`reconcile_force`, `deploy_force`, `apply_secrets`, `apply_enable_change`) is a distinct id so it must be *asked for* and the audit line names it, with no combined shape because "two overrides in one call is two decisions in one"; reversible verbs (`shutdown`/`resume`, `shed`/`unshed`) skip the token so an unattended NUT hook works. The red team found ten confirmed issues and the layered model held. This is transferable to any project.

**Deterministic core, thin adapters — enforced, not aspirational.** Library modules raise typed `SyrvisError`s with stable `code` strings and never print; `cli.py` is the only presentation layer; `--json` is the machine contract that the MCP passes through untouched. Three adapters exist and none re-derives platform semantics.

**Stage-then-swap, three times, plus a digest-verified restore.** Install builds in `.staging-<v>`, moves the old aside rather than deleting it, and rolls back on any failure; `postupgrade` builds `venv.new` and verifies in staging; restore checks the sidecar digest, extracts to `.restore-staging/`, compares every member against `file_digests`, rebuilds the venv from the cached wheel *before* the symlink moves, and rejects traversal in `_safe_dest`. The symlink is truth and the manifest mirrors it.

**Intent lives outside the declaration set.** `shed` in `data/state/intent.json`, with the composition rule stated in one sentence ("a workload runs iff the device is `in-service` AND the service is `enabled` AND the service is not shed"), pinned over any incoming bundle, and `unshed` starting nothing — "one bring-up path, not two." This is the single best structural fix of 2026 and it generalizes.

**Buckets, not failures — and alarm hygiene as a design concern.** `disabled`/`shed`/`terminal`/`blocked` are report rows, not actions; a hard edge onto a shed target is a plan-time bucket so "a deliberate 14-service load-shed must not fail every hourly reconcile"; the dashboard fold excludes shed from unhealthy because "an amber that never clears is an amber nobody reads"; 0.5.13 un-armed a permanent red because "a liveness gate only goes red for states someone can fix." Very few systems treat false alarms as bugs.

**Three-valued honesty everywhere.** Absent ≠ unparseable ≠ empty: the journal's `unknown` verdict, the DSM census reporting `ok:false` on unrecognized output ("'the census could not run' and 'there are no other tasks' must never look the same"), `absent beats invented` in `/api/summary`, unreadable mdstat meaning "no evidence" never "assume one."

**Per-file isolation with a strict/tolerant asymmetry that is named as a boundary.** One bad declaration invalidates only itself; unknown keys are rejected on every write path and dropped only for read-only display, with the reason stated: the deploy path "must NEVER silently ignore an unaudited key — that rejection is the trust boundary."

**Refusals that carry the recovery, and alarms stored outside the failure domain.** The collision precheck ("prose is not a guard"), `start-stop-status` exiting 1 so DSM's package status goes red, the rootfs `syrviscore-boot.env` cache because "the alarm was stored inside the thing it was supposed to alarm about," and the deliberate deletion of the destructive advice ("Run `syrvisctl install`" is the one that makes it worse).

**Supply-chain posture.** Digest-pinned core images, no `:latest` anywhere including L2 declarations, SHA256SUMS verified by default with an explicit opt-out, an offline `--no-index` SPK install from six pinned wheels, a release-attached `config.yaml` as the image-bump channel, and an owned non-root distroless exporter replacing an anonymous unmaintained root container.

**The `dev-loop` CI job.** Build devkit → bootstrap → `rm -rf` the home → restore → re-verify. It is the one place a real venv, real pip and a real disaster recovery run, and it buys back exactly the fidelity the hermetic fakes cost.

**Comments as provenance.** Nearly every non-obvious constant, refusal and ordering choice carries the dated incident that produced it, often with the falsified sentence left struck in place. It is why this retrospective was possible at all, and a rewrite that keeps the code and drops the comments would lose more than it kept.
