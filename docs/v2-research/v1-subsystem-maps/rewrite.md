# Rewrite analysis

## Language & runtime evaluation

**Verdict: Go for everything that runs on the NAS; Python 3.12 + uv for the operator-side MCP only; not Rust.**

The Python 3.8 pin is not a Python decision — it is a *distribution* decision wearing a language costume. CLAUDE.md says so outright: 3.8.12 "exists ONLY for SyrvisCore/DSM parity." Every other repo in the portfolio targets 3.12. So the honest question is not "is Python good enough" but "what does shipping an interpreted runtime onto DSM actually cost," and the maps price it precisely:

- **Toolchain tax.** Black is frozen at 24.8.0 repo-wide because "26.x already reformats source 24.8.0 accepts" and 24.8.0 is the last release installable on 3.8. CI pins `ubuntu-22.04` because "Python 3.8 is unavailable on newer runners." There are two pyenv environments (`syrviscore` 3.8, `syrviscore-modern` 3.12), two `make check` targets, and three test suites that **cannot be collected in one process** (`ImportPathMismatchError` on colliding `tests.conftest`). 91 tests in `packages/syrviscore/tests/` are run by nothing, unlinted, because `testpaths = ["tests"]`.
- **Cross-boundary drift as a language artifact.** `_cli_regexes.py` copies the CLI regexes *verbatim* rather than importing them, with the reason in the file: the MCP "must NOT import the syrviscore packages (they target Python 3.8 and pull in docker)." `commands.py`, `STACK_SERVICES`, `RESERVED_NAMES`, `MIN_BOOT_HOOK_CONTRACT` are all duplicated-with-drift-tests for the same reason. That is an entire class of debt whose root cause is "two runtimes that cannot import each other."
- **Venv-per-version machinery, which a static binary deletes wholesale.** `install_version` builds a tree in `.staging-<v>` and then `_fixup_relocated_venv` rewrites the staging path out of every console-script shebang; SPK `postupgrade` builds `venv.new`, re-verifies in staging, swaps, then rewrites baked paths in `bin/*` *and* `pyvenv.cfg` for **both** the symlink form and the `readlink -f` form; `preinst` hard-fails on missing `ensurepip`; `build-manager.sh` pre-downloads six pinned pure-Python dependency wheels for offline install; `set_tree_readable` chmods the entire tree 644/755 on every install. The live consequence is measured in the vision maps: `versions/` at **962 MB with 40 versions retained** against a default keep of 2. Replace the venv with one file and the entire staging/relocation/permission apparatus becomes `write`, `verify sha256`, `os.replace`, symlink.
- **The interpreter itself is uncontractual on the target.** The owner's own design/61 already ruled on this: rootfs python3 "is Synology's private dependency and can move or vanish at a major rev, which is precisely the event this agent must survive," and static Go "sidesteps DSM's glibc jump (2.26 → 2.36 inside the 7.2 line)." That ruling was made for the host agent; it applies verbatim to the platform.

**Staying Python (3.12 + uv), evaluated seriously.** uv genuinely fixes the toolchain half: one environment, one formatter, standalone interpreter builds, fast CI. It preserves ~2,038 gated tests that are the institutional memory of a dozen named incidents — the single strongest argument against any rewrite. But it fixes nothing structural. You still ship an interpreter tree onto DSM (a uv-managed standalone python is ~50 MB unpacked and reintroduces relocation fixups), you still cannot import the platform from a modern-Python adapter unless *everything* moves to 3.12 at once, and you still have zero compile-time protection against the drift class that actually bites here. The 0.5.12 bug is the case study: `RestartCount` was read from `attrs["State"]` — "a location Docker has never populated" — and it shipped **inert past 1,100 tests** because `_FakeContainer` fabricated the field. A typed Docker API client makes that a field that does not exist. Same shape as the MCP's `_KIND_VALIDATORS` covering 16 of 18 registry slot kinds: a bare `KeyError` escaping as a raw traceback, in the one table nobody generated. Both are "shapes that agree at test time and disagree in production" — exactly what a type system and exhaustive switches buy.

**Rust: no.** The security boundary here is argv construction, sudoers enumeration and charset allowlisting — not memory safety. Nothing in the audit or the 2026-07 red team (23 candidates → 10 confirmed) was a memory bug; F3 was shell word-splitting, F1/F2 a fail-open allowlist, F7 a check-then-add race. Rust buys the wrong safety, costs an async runtime for the socket/HTTP surface, and lands on a single maintainer whose house language is Python. The one Rust advantage that would matter — no GC pauses — is irrelevant on a box where the tightest deadline is a 150-second rc.d stop window.

**Go's specific fit here.** The FFI need is trivially met: only `docker_manager.py` imports the Docker SDK; everything else already shells out (27 `subprocess` sites in `privileged_ops`, 17 in `service_manager`, 12 in `validators`), and compose is driven by argv with a v1/v2 probe. Go's stdlib talks to `/var/run/docker.sock` with a custom `http.Transport` and no dependencies — design/61 already specified exactly that. `os/exec` with contexts gives bounded subprocess execution with real timeouts, which is what `synowebapi`, `synoschedtask`, `ip` and `git` need. And for LLM-assisted maintenance, Go is the best of the three: one package per concern, gofmt removes formatter debates entirely, `go vet` + exhaustive switches catch the registry/validator drift at build time instead of at `resolve_slot`, and cross-compiling a linux/amd64 static binary from the Mac needs no Docker and no CI runner.

**Keep Python where it already is modern.** `syrviscore-mcp` runs on the operator's Mac at 3.12 and never touches DSM. Leave it, move it to uv, and regenerate it from the API schema (below) so the 77-registry-commands-vs-50-tools gap becomes structurally impossible.

## Architecture from scratch

### 1. A resident agent, not a one-shot CLI

Every state file in `data/state/` exists to fake continuity across process deaths. `is_flapping` infers a crash loop from one sample because "an engine that has to remember a previous observation to notice a crash loop cannot notice one across a restart of itself." The deploy journal reconstructs "is a run in flight" from a pid and a 3,600-second staleness rule. `bringup.json` / `bringup-pending.json` / `bringup.lock` (design-only) are three files inventing a process table. The boot hook polls `docker info` for up to 600 s and retries `reconcile` three times because nobody is home. `seam-selfheal` is a `*/5` cron because nothing is resident. And design/61 is 1,320 lines specifying the daemon the platform keeps approximating in shell and JSON.

The decisive argument is concurrency. The service package contains **no `flock` at all**. Cron `schedule apply`, the S99 boot hook, `syrvis reconcile`, seam `apply`/`deploy` and the dashboard all read-modify-write `config/services.d`, `intent.json`, `breakers.json` and `/etc/crontab` with only per-file `os.replace` atomicity between them. Two concurrent sheds lose a row. `instance_bundle._write_declarations` unlinks under an in-flight reconcile that already loaded the set. Nothing tests any of it.

**Design: `syrvisd`, a rootfs-resident static binary, the single writer for all derived state.** It owns the reconcile loop, the flapping window, the breaker engine (design/63 M2, specified and unwired today), the journal, boot orchestration, the seam-shell heal, schedule apply, and the shim. Serialize every mutation through one in-process queue and the entire TOCTOU/locking class disappears — not mitigated, deleted.

The CLI stays, as a **thin socket client** with one exception that the maps make non-negotiable: a `--local` rescue mode that works with the daemon dead and no resolvable home. That is `syrvisctl doctor`'s lesson — "the one read that answers with no resolvable home… the 22-method self-audit contains not one check that looks at a volume root."

### 2. API-first; the CLI is generated

Today one operator call is parsed three times: the MCP builds argv from the registry, ssh re-joins it into a string, the forced-command shim re-splits and charset-validates it, then sudoers glob-matches it, then Click parses it again. That layering is honest defense-in-depth (G13 exists because "OpenSSH re-parses remote args through the remote shell"), but it also *deforms the design*: `schedule apply` takes no cron argument because `*` and `,` "would fail the shim char-allowlist," so a schedule must travel as file content. The sudoers globs are "much looser than the shim." Eighteen slot kinds exist solely to describe how to spell values safely in a shell.

**Make the wire format a typed request, not a command line.** One versioned API schema (methods, typed params, read/mutating/destructive classification, timeouts) is the single source of truth. From it, generate: the CLI's command tree, the MCP's tool definitions, the dashboard's typed client, and the authorization table. This is the same G18 idea the seam already proves works — "the enumerated sudoers boundary and the shim allowlist are derived from the same source the runtime uses to build argv, so they cannot drift" — applied once instead of three times, and with generated adapters that cannot lag the way 50-of-77 tools did.

### 3. State store: SQLite, one file, one writer

The maps document a hand-rolled database with six independent schema integers (manifest 3, backup 1, intent 1, journal 1, breakers 1, runstate v1) and no query layer. Revision numbers are claimed by `os.link` with a 1,000-attempt retry loop. Retention is "newest 50 per workload," and at the cap "a rollback target simply disappears with no warning." The journal caps at 500 events; breakers cap at 512 rows, "closed rows dropped first." Shed rows are never garbage-collected and a shed row for a deleted declaration "persists forever and still blocks dependants." `read_intent` accepts strings `validate_intent` rejects, so a hand-edited file reads fine and then poisons the next unrelated write. `_last_deploy_sync` compares ISO strings lexically. `apply_instance_bundle` "is not transactional across sections… recovery is documented as re-run apply."

Every one of those is a database feature someone re-implemented by hand, once per file.

**Design: `state.db` (SQLite, WAL, single writer).** Tables: `revisions`, `events` (the journal as a genuine append-only log with indexed queries instead of a 500-entry ring), `breakers`, `intent`, `runstate`, `versions`, `kv`. One `PRAGMA user_version` migration ladder replaces six schema integers. Transactions give `apply` the cross-section atomicity it lacks. Retention becomes a `DELETE … WHERE` with a policy, and "the rollback target vanished silently" becomes a query that can *say so*.

**The line to hold: declaration is files, memory is database.** `config/services.d/*.yaml`, `.env`, `stack.yaml`, `shares.d`, `jobs.d` stay plain text — that is the substrate ("the file collection is the substrate; every explicit interaction is sugar that writes those files"), it is what lets home-tech push with `rsync`, and it is git-diffable. Observed and derived state goes in SQLite. Nothing that a human or another repo must author lives in the database; nothing the daemon derives lives in a file.

### 4. Level-triggered reconciler; every verb writes intent

The platform already has three mechanisms holding a service down — `enabled: false`, shed, and `restart: no` + terminal — and its own comment on the third reads "Three mechanisms, one field, cancelling out." `service stop` writes *ephemeral* intent that the next GitOps apply overwrites; the durable one (`shed`) had to be invented after "fourteen load-shed services could be resurrected, mid-array-resync, by a runbook whose own text said they would stay down."

**Shed was the right shape; make it the only shape.** Every imperative verb becomes an intent write, and one level-triggered loop converges. `stop` is a shed with `reason: operator`. `unshed` already "starts nothing — reconcile does"; generalize that to all verbs: **one bring-up path, not two.** The composition rule stays exactly as written: *a workload runs iff the device is `in-service` AND the service is `enabled` AND the service is not shed.*

A resident level-triggered loop also retires the current write-only doctrine: the breaker engine has a caller (the loop consults `should_attempt`), the journal has a reader, `blocked` re-evaluates every tick so lifting a shed unblocks dependants with no operator action, and flapping is observed rather than inferred. Keep the plan/apply purity split verbatim — it is the best-tested thing in the repo, and it is what makes dry-run "side-effect-free by construction."

### 5. Orchestration: direct Docker API, not compose; not k3s, not podman

**k3s: reject.** The entire routing model exists because DSM's nginx owns 80/443 and the Application Portal refuses 443 proxy rules — that fight does not get easier with a CNI and a servicelb on top of Synology's Container Manager. The design corpus is simultaneously trying to hold SYRVIS_HOME to a 1.5–2 GB "light payload"; a single-node control plane's write volume is the opposite direction. And the standing failure mode is "one cold boot renamed a volume root and decapitated the platform for 50 minutes with no page" — adding etcd/kine to that blast radius is strictly worse. One maintainer, no staging environment.

**podman/quadlet: conceptually the closest fit, reject on platform.** Declaration files → units → a supervisor you did not write is exactly the right shape. But DSM offers no supported systemd surface for this, Synology ships Docker, and switching runtimes abandons Portainer, the docker socket, docker-socket-proxy and the whole metrics plane in one move. Note the idea and move on.

**Drop compose as the source of truth; drive the Docker API directly.** Compose is already only an intermediate serialization the platform writes and immediately shells out to — and then has to *work around*: `depends_on` is deliberately never emitted because it means something different here; `up -d` "compares the compose spec, not the content behind it," so design/60 G1 needs a bundle-digest comparison plus a force-recreate-vs-restart fix-up; `remove_disabled_core_containers` exists because `--remove-orphans` is too wide; each L2 service gets its own project purely for isolation; `compose_cmd` probes v1 vs v2; the emitted file still carries an obsolete `version: "3.8"` key.

With direct API calls, the container spec is typed, ownership is a label (`syrvis.service`, `syrvis.spec-hash`), and "does the running container match the declaration" is a hash comparison against a label — which is precisely what G1 hand-built from digests and history records. That collapses: the two independent drift notions (`drift.py` vs the planner, which "can disagree"), the recreate-vs-restart verb distinction (the loop recreates iff the spec hash changed), the compose-probe, and the double compose generation per save. Keep `syrvis compose export` as a *projection* for humans and Portainer — a debug artifact, never the truth. The cost is honest: you own restart policy, readiness and dependency waits yourself. You already do — design/63 chose `restart: no` over `on-failure` on determinate moby internals, and 15 of 39 services have no healthcheck, so "healthchecks absorb that" was already ruled "a hope, not a mechanism."

### 6. The seam, redesigned: UNIX socket + capability grants, ssh as pure transport

Three of the seam's six layers exist only because the wire format is a shell string. Delete the string.

The agent listens on `/run/syrvisd.sock` (root:syrvis-operator, 0660). The operator key keeps `restrict,command=…,from=…`, but the forced command is a subcommand of the same binary: read a length-framed JSON request from stdin, forward to the socket, stream the response. **No argv on the wire at all** — which is already how `apply`, `deploy`, `secret set` and `config set` work, and they are the only verbs where secrets are structurally safe. Generalize the exception into the rule.

Authorization moves from "sudoers globs + 291 lines of POSIX-sh charset matching" to an in-process role check against the caller identity (SO_PEERCRED locally; the key id from the forced-command environment remotely), with one role table shipped and versioned with the binary. That retires, by construction: sudoers globs looser than the shim (`service task --task * -- *`); the shim's charset allowlist deforming the schema; `syrvis-reader` being "half a citizen, healed and doctored, never provisioned"; the three duplicated copies of the `/etc/passwd` seam heal (a forced command that is the agent's own subcommand needs no login shell, and the agent heals its own accounts at boot from the rootfs); the auto-seam-sync trust hole where rolling back below 0.4 leaves the boundary "wider than the running version, i.e. it fails open on width"; and `privilege.self_elevate`'s `sudo <python> <argv>` — "an argv shape that is not in the sudoers policy," a second privilege model coexisting with the enumerated one.

Keep, unchanged: the dedicated least-privilege account, `restrict` + `from=`, the two-call confirmation handshake with per-process salt for destructive verbs, the deliberate break-glass floor (`setup`, `restore`, `--purge`, `reset` stay off the seam — "disaster recovery must not depend on the thing being recovered"), and secrets never touching argv, ps, logs or an LLM context. Upgrade the audit log, which today has "no timestamp, no rotation and no size bound" for a file "explicitly described as a security record."

### 7. Packaging: the SPK survives, the venv does not

Keep the SPK — v2-design's reason still holds: "its primary justification is disaster recovery… This makes the SPK's reliability a DR requirement, not a convenience." But it becomes a file drop: one static binary, an rc.d hook, a boot-env cache. Deleted: unprivileged-package-user venv creation, the offline wheel bundle, the `ensurepip` hard-fail, `_fixup_relocated_venv`, `pyvenv.cfg` rewriting, `postupgrade`'s `venv.new` swap, `set_tree_readable`.

The manager/service split existed because a venv is expensive and mutable. A binary is neither, so collapse to **one binary with subcommands** — but keep the split's actual value as `--rescue` on a **rootfs-resident** copy. That is strictly better than today: on 2026-08-16 the rootfs S99 hook survived and the volume-resident wrapper, seam, cron heal and startup script all died together. Versioning becomes: download file → verify sha256 → symlink. Rollback is a symlink swap of a file, which is what "instant rollback" always claimed to be.

Non-negotiable additions: CI must build and validate the SPK and the binary (today **no CI job builds an SPK at all**, so error-263/313 regressions are hand-caught), and `spk/INFO`'s stale `0.1.21` and the four-year-old docs go with the rewrite.

### 8. Adapters

**Fold the dashboard backend into the agent.** It is already an in-process library import; making it an HTTP handler in the same binary eliminates the pin-lockstep failure class outright — two silent-blindness regressions in three image releases (0.5.9's over-strict `SYRVIS_HOME` check "emptied the dashboard's entire Layer-2 list, silently"; 0.5.10's bundled lib returning "an EMPTY L2 list with `error: None`… the lockstep trap's worst variant"), the `tolerant=True` reader that exists only because the image bundles its own copy of the library, and the design/63 D2 reader-enumeration gate that CLAUDE.md enforces in *prose*. Ship the SPA as static assets served by the agent behind Traefik; the container tier keeps only what genuinely wants isolation.

**MCP stays Python on the Mac**, moves to uv, and becomes a generated client of the API schema. Its validators become UX, not security, because authorization is server-side and typed.

## What to keep

These survive any rewrite, as principles:

1. **Declarations are files; the file collection is the substrate.** One mechanism, four front doors. Everything imperative is sugar that writes those files.
2. **Deterministic core, thin adapters.** "Anything an adapter can do, `ssh nas && syrvis …` can do." No operation may exist only via MCP or dashboard.
3. **Per-file validation isolation.** One bad declaration invalidates only its own file — never the set.
4. **Strict on write, tolerant on read.** The write path is the trust boundary; an unaudited key must never be silently ignored there.
5. **Intent is durable and lives outside the declaration set.** `runs iff device in-service AND enabled AND not shed.`
6. **Refuse rather than guess.** Ambiguous home, collision artifacts, non-empty relocation, unmounted volume, vanished app home, the empty-config floor check. "An empty config is never a reason to act on a populated instance."
7. **Name the state; never infer it.** Absent ≠ unparseable. Unknown is never a pass. `not_configured` is not a failure. Shed is not unhealthy — "an amber that never clears is an amber nobody reads."
8. **Guards are overridable, and the override costs evidence.** "The refusal and the bypass cost the same one line."
9. **Plans are pure.** Dry-run safe by construction, not by discipline.
10. **Anything two components must agree on is generated from one source** — and prose is not a guard. The tag gate and the rollback prohibition belong in CI.
11. **The alarm must not live inside the thing it alarms about.** Rootfs caches, external deadmen, a red DSM package status as "the cheapest out-of-band signal."
12. **Reserve-first budgets.** Stores keep their declared grace; consumers clamp into the remainder. Verify the transport window before trusting the budget.
13. **Secrets transit stdin/socket only.** Never argv, never a laptop file, never an LLM context.
14. **Stay generic.** Exposure is declared intent; the platform never touches DNS or a Cloudflare API. Every incident becomes a named test.

## Migration paths

**(a) Incremental refactor in place.** Move to 3.12 + uv, unify the two environments, adopt SQLite for `data/state/`, wire the breaker engine and the journal, fix the backup layout bug (`_gather_backup_items` captures none of the located app homes for 15 services), adopt the orphaned 91 tests. *Effort:* 4–8 weeks part-time. *Risk:* low per step. *But:* it deletes no structural cost — venv-per-version, the argv seam, the shim/sudoers pair, the dashboard lockstep, the four writers of one boot hook all survive. And the 3.8→3.12 step alone forces shipping an interpreter, i.e. paying a static binary's distribution cost without getting one.

**(b) Strangler: new Go agent alongside; verbs move over.** Build design/61's `hostd` as `syrvisd` — it is already specified at 1,320 lines, already ruled Go, already has placement, release, checksum and update-survival stories. Give it three things first: (1) **boot orchestration and self-heal**, the highest-value/lowest-coupling piece and the exact thing that failed on 2026-08-16; (2) **the state store**, single-writer from day one; (3) **the reconcile loop plus the breaker engine**. Then migrate verbs one at a time — each becomes a socket method, the Python CLI becomes its client. The forced command becomes the JSON proxy once the last argv verb moves; the dashboard backend folds in; the SPK drops the venv when the last Python verb is gone. *Effort:* months, but every step ships and is independently revertible. *Risk:* a dual-writer window on state — mitigated by one invariant enforced from the first commit: **the Python side never writes `state.db`; it calls the agent.** Port each module's incident tests to Go table/golden tests as its verbs migrate; keep the Python suite green until the module is deleted.

**(c) Clean rewrite plus state import.** The importer is genuinely easy — six JSON schemas plus YAML declarations that do not change shape. But it discards 2,038 gated tests that encode a dozen named incidents, and the surfaces it would have to re-derive are precisely the untested ones: `setup` 11%, `doctor` 9%, `privileged_ops` 43%, Docker never exercised at all, no SPK ever built in CI. With no staging environment, re-deriving those against a production NAS is a return to the condition the July 2026 audit named: *"the NAS was the integration test."* Reject.

**Recommendation: (b).** With three hard gates. First, no verb migrates without its incident tests ported — the tests are the design record, and losing them is the only irreversible cost in this plan. Second, CI builds the SPK and the binary from day one, because the artifact DSM actually installs has never been gated. Third, ship the agent's own rescue path (`--rescue`, rootfs-resident, no volume dependency) *before* it owns anything important — the platform's worst outage was caused by trusting a volume path, and the replacement must not repeat it on its first boot.
