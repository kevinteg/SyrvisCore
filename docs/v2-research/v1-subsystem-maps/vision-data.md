# THE VISION — DATA PLANE, VERTICALITY & OWNERSHIP (home-tech design corpus)

## Purpose & role in the system

SyrvisCore is the *execution engine* for a data doctrine it does not itself author. The doctrine lives in `~/code/home-tech/design/` and answers three questions the platform is built to serve: **whose bytes are these** (ownership), **where do they physically sit** (placement), and **what proves they come back** (backup/lifecycle). The division is stated as design/00 D10 — *"**D10 ✅ SyrvisCore stays generic.** Everything above lives in home-tech… Items that require SyrvisCore changes… are spec'd here as contracts and handed to the SyrvisCore repo as its backlog"* (00:222–225) — and reinforced by design/26 §7: *"SyrvisCore ships the **generic** `data_volume` field + the containment fix (it never names `/volume6` or Onyx); home-tech **declares** `data_volume: /volume6`."*

The vision, in one line: **every byte on the NAS has exactly one declared owner, one declared home, one declared backup story, and one declared lifecycle stage** — and the platform's job is to be a validated, refusal-guarded *placement executor* for that declaration set, never to infer semantics.

## How it actually works

**The contract (design/45 §1).** Every NAS byte is exactly one of: **(a) service-owned** — container data under a SyrvisCore-managed service, declared in `data.d/`, reconciled by the seam; or **(b) repo-owned file-share data** — a subtree of a DSM share with all four of: a declared owner repo, a content-addressed manifest *committed in that repo*, a named ingest contract, and a per-subtree GC class. *"**No orphan data.** A share, or a top-level directory inside a declared share, that no registry entry claims is a verify failure, not a curiosity"* (45:78–79). The single escape hatch is `manifest: owner-waived` with a `waiver_reason:` (D1), enumerated so the exception list cannot grow silently.

**Registry shapes.** `syrvis/data.d/<id>.yaml` (design/18 §3) carries `{id, owner_app, owner_repo, path, kind: media|database|config|documents|metrics|cache, sensitivity: low|medium|high, regenerable: bool, backup: {method, job, destination, encrypted_at_rest, schedule, retention}, restore: {runbook, verified}}`, extended by design/45 §4.2 with a `fileplane:` block (`{share, manifest: {repo, repo_path, hash, check}, ingest, gc: {<subtree>: precious|reproducible|inbox}, signpost}`). `syrvis/shares.d/<share>.yaml` (45 §4.1) carries `{id, share_name, volume, class: inbox|resting|legacy-frozen|service|personal, protocol, hide_unauthorized, recycle_bin, sensitivity, acl: {<principal-slug>: rw|ro}, datasets: []}`. Design/53 §7.3-4 replaces the old two-method `SWEPT_ROOTS` dict (`render/data.py:88`) with `syrvis/backup-tasks.d/<task>.yaml` = `{id, dsm_task_name, encrypted, destination, roots[]}`, and data.d rows name their task (`hb:<id>`).

**Lint rules 1–15 are the enforcement** ("an un-backed or mis-encrypted dataset is a **build failure**, not a forgotten runbook bullet", 18 §3): `regenerable: false` + `method: none` → ERROR; `sensitivity: high` + `encrypted_at_rest: false` → ERROR; `path` must map to a real `services.d` volume; `backup.job` must exist; plus 45's 11–15 (resting shares list ≥1 dataset with a two-way link; GC vocabulary closed; manifest-or-waiver, no third state; inbox shares carry no datasets; `anton` on a family share is an ERROR). Design/18 §3 adds the **inverse rule** (2026-08-16, ops:F30): every `services.d` service with a `volumes:` entry needs a `data.d` row or an explicit `data_exempt:` — because *"the registry can silently shrink"*.

**The L1/L2 boundary (design/53 D1 — "the light payload").** SYRVIS_HOME (`/volume4/syrviscore`) contains, exhaustively: `bin/ versions/ current`, `config/ services/ compose/ jobs/ hooks.d/`, `data/deployments/ data/state/`, L1 core data (traefik/portainer/cloudflared/dashboard), `backups/` (manager tarballs only), plus two declared exemptions — L2 **rendered-config-only** dirs and L2 **bounded transient spools** (vector 88 M, vmagent buffers, alertmanager silences), each carried as a `kind: cache` data.d row *"so the exemption is visible, not silent"*. Target steady state ≈ **1.5–2 G**.

**Placement mechanism, as shipped.** `location: /volume<N>` re-homes an app to `<location>/<SYRVIS_APPS_ROOT_NAME>/apps/<name>/{data,config,secrets,logs}` (26 §8.1 as corrected). Slot mapping is semantic: a volume source named exactly `config` → `home/config`, `logs` → `home/logs`, anything else → `home/data/<source>`, and a source named `secrets` is **refused** (env_file is the secrets mechanism). Guards, all live in SyrvisCore 0.5.17: `LOCATION_RE = ^/volume\d+$` (`service_schema.py:48`); authorship gate against `OPERATOR_AUTHORED_PREFIXES` (`service_manager.py:3294`); mounted-volume refusal at `_generate_compose_file`, the shared start choke point; containment assertions per slot; and `LOCATION_CHANGE_REFUSAL` while the current data root is non-empty.

**Per-volume placement (design/37 §4) shipped in 0.5.16** and is verifiable: `_validate_volume_locations` (`service_schema.py:601`) requires `location:`, rejects non-declared volume names, forbids overrides on `config`/`logs` and infra mounts, revalidates `LOCATION_RE`, and rejects overlapping keys; `service_manager.py:1485` enforces `is_mounted_volume` per override; `_volume_location_change_refusal` (`service_manager.py:687`) is the per-VOLUME immutability guard, with the rationale recorded in-code: *"a nested bind SHADOWS what is underneath rather than merging it… the app would come up looking freshly initialised"*; `service_manager.py:1691` writes `# volume_locations: {} -> {}` into the generated compose so drift inspection stays legible.

**The file-plane bind (`fileplane=`)** is the sibling primitive for bulk that belongs to a *declared share* rather than an app home. `shares_registry.py` (139 ln) reads a deliberately minimal slice of `$SYRVIS_HOME/shares.d/*.yaml` — `{id, share_name, volume, class, writers}` — and ignores every other key *"so a deployment repo may keep richer semantics (ACLs, backup scopes, sensitivity classes) in the same files without coupling the engine to them"*. Resolution is by ID only; absolute host paths stay refused; `class: resting` gates rw binds behind the share's `writers:` sanction; an undeclared share is a typed error at deploy/render time — *"an unbindable share is the feature working."*

**Placement doctrine (design/64 D1).** A volume is `fast` (small, quick to resync, device-independent of bulk arrays) or `bulk`. Service-critical state → fast; bulk data → bulk. The invariant: *"degrading any bulk volume (resync, scrub, disk test, expansion) may slow DATA access but must leave every service alive, healthy, and — for the monitoring plane — fully functional."* D4 makes bulk degradation a **SOFT** condition: no graph edge may target a volume; healthchecks on bulk-homed services probe liveness never deep IO; and the amendment states the limit honestly — *"the D1 invariant covers SLOW volumes only"*; an unmount is an outage that opens breakers and requires an operator `syrvis up`.

**The lifecycle ambition (design/50).** The unit is the **vertical** — one domain's bundle across repo, NAS trees, edge site, services, corpora, streams, skills — declared by a colocated `vertical.yaml` (`vertical/v1`), glob-discovered, never a registration roster. The model is five stages: `retrieve → store-raw → process → present → interact`, each declared complete-or-`na`-with-reason, graded PASS/WARN/FAIL by `make introspect --json` which *aggregates* existing verbs (`make freshness`, `validate.py`, `sync.sh --check`, the repo's own `manifest_check`) and reimplements nothing. The `store-raw` stage is exactly design/45's machinery; the `.data-plane.yaml` on-disk **signpost** (pointer, not ledger) is what lets a human standing on the NAS answer "whose is this, where's the ledger, what may be deleted".

## Design decisions & their rationale

- **D10 / design/51's two-reconcilers boundary** — home-tech declares placements, the platform executes them (53 §6.4: *"Two-reconcilers boundary (design/51): intact"*). This is why `shares_registry` consumes but never creates shares.
- **Placement is a validated platform field, never convention** (53 D5): *"the design explicitly rejects convention-only bind mounts"*. The symlink workaround was rejected because *"the placement stays invisible to SyrvisCore — backups, prune, drift all reason about the wrong path"* (26 §2).
- **`volume_locations:` is mechanical, not semantic** (37 §4): *"it places named volumes; it does not know what 'artifacts' or 'metadata' are… The moment it grows semantic classes ('artifacts', 'cache') it starts duplicating `data.d` — reject that in review."*
- **The share-name rule, learned the hard way** (45 §4.1 amendment / 53 §2): *"a DSM share name must never equal any plain volume-root directory name on any volume."* The falsified sentence is left struck in place: *"~~No name collision: DSM's share namespace doesn't contain `syrviscore`~~ **← FALSIFIED 2026-08-16. This sentence is the landmine.**"* One cold boot, `synocheckshare` at ~142.8 s, renamed both plain roots to `syrviscore_1` and decapitated the platform. The remediation is `SYRVIS_APPS_ROOT_NAME` — and the platform encodes the lesson: `paths.py` refuses a segment ending `_<digits>` because *"that is the suffix DSM hangs on a collision-renamed volume root, and a segment wearing it would make the boot reclaim guard unable to tell configuration from damage."*
- **Family photos move once, into the app model, not a browsable share** (53 D3): *"Nobody may browse an Immich media root"*; a `Photos` share would gate 224 G on a 0.6 feature or force a second migration. Legibility rides the registry, not the path string.
- **SMB invisibility is ABE, not the browse-list checkbox** (53 D8/§5): macOS enumerates over MS-RPC `NetShareEnum` and does no client-side hiding; the fix is service-level *"Hide shared folders from users without permission"*. Crucially, *"Hyper Backup is unaffected: it is a DSM package reading shared folders from the volume, not an SMB client"* — the property §2's whole construction rests on.
- **Manifests live in the owning repo; disk carries a signpost, never a ledger** (45 D6), with a minimum contract only (hash + bytes + relative path + tier) because *"Forcing one format would buy nothing and break three working systems."*
- **Registries unify, never multiply** (50 D9/Q7): a ninth registry was rejected; central registration *"is the pattern that produced the roster ghost".*

## Invariants & contracts other subsystems rely on

1. `<location>/<SYRVIS_APPS_ROOT_NAME>/apps/<name>/{data,config,secrets,logs}` is the app-home shape; **the segment is read from `deployment.yaml` `tuning:`, never hard-coded** (26 §8.1 correction — `render/data.py` hard-coded the literal and *"went blind at the rename"*).
2. `SYRVIS_HOME = /volume<N>/syrviscore` is **not** configurable (`paths.py:63–69`) — the wrapper, sudoers and SPK bake it. Only the apps root moved.
3. Refuse-don't-corrupt: unmounted volume ⇒ refuse to materialize; non-empty current dir ⇒ refuse a location or per-volume change. Design/26 §8.5 lists both as the release-blocking findings that were fixed.
4. `/volume6` is never swept — *"dumps are the backup surface"* (26 §8.4) — with the rule of thumb added 2026-08-16: *"a tenant may only live on a no-sweep volume if something declares how its bytes come back."*
5. Immich I4 (never split `upload/` from `library/`) and I6 (free space watched only at the media root) bind any future `volume_locations:` split.
6. Records/anon boundary: `syrvis-reader` gets no ACL; `data.file-plane` reports SKIP-with-note — *"a deliberate coverage hole, declared rather than papered over."*

## Gaps, debt & sharp edges

**Exists in the platform today (0.5.17):** `location:` + the v2 app home; `SYRVIS_APPS_ROOT_NAME` (0.5.14) with `validate_apps_root_name`; `check_home_collision` / `check_apps_root` (`validators.py:516,668`) including the armed-⚠ case; `volume_locations:` (0.5.16) with per-override mount checks, containment, per-volume change refusal, purge coverage and the compose comment; `fileplane=` binds + `shares_registry`; durable `shed` intent (0.5.15).

**Still vision:**

- **`syrvis share declare|list` does not exist.** The platform *consumes* `shares.d/` and cannot create or reconcile a share (design/51 D5 "BUILD 3"). Every share is hand-made in the DSM UI — which is precisely how the collision landmine got armed. Ownership of share creation is unclaimed by any engine.
- **`syrvisctl backup create` is still location-unaware — verified.** `_gather_backup_items` (`syrviscore_manager/backup.py:156`) walks only `home/config`, the L1 data dirs, `services/`, `compose/`, and `home/data/<svc>`. A relocated app's `config/` and `secrets/` slots on /volume5 or /volume6 are outside backup scope, exactly as design/53 §6.2-2 predicted — *"the one genuine 0.6 platform bug this design surfaces"* — now covering 15 located services. Restore convenience, not data loss, but undeclared in the archive's own manifest.
- **`data_location:` / share-path homes** (53 §6.2-1) unbuilt; consequence: `immich-legal`'s at-rest parity (OQ1) is unresolvable, and D7's residual — immich-server's config/secrets slots riding /volume5 because its 224 G upload does — persists until a `volume_locations:` split is declared.
- **`nas.location` pre-deploy check** promised in 26 §8.5, still absent (`grep nas.location scripts/verify-all` returns nothing); re-ruled 2026-08-16 as "keep it, build it small".
- **`syrvis/volumes.yaml` + `intent.placement` lint** (64 D8) was asserted done and was not in the tree; and the lint's primary key is a **no-op**: exactly three declarations carry `critical: true` and *"all three are volume-less"*, so *"not one database in the fleet is validated by it."*
- **`.data-plane.yaml` is broken in both directions**: six datasets declare it, *"no code writes or reads it"* — *"Six declarations asserting a file that nothing produces or verifies is worse than no declaration: it reads as coverage."*
- **The rename disabled the lint written to catch renames** (18 §3 ops:F28): rule 8's hardcoded `/volume\d+/syrviscore/` regex silently skips twelve repathed rows — *"the guard's failure direction is a **silent skip, not a finding**."*
- **design/50 is 0-of-11 implemented**; `make introspect` *cannot* exist because home-tech has no `Makefile` at all.
- **A red build gate stops being a gate**: `data.coverage` FAILs on a deliberately committed row, so the next unintended ERROR is indistinguishable. Proposed fix: `accepted_gap: {reason, owner, design, review_by}` → dated WARN.
- **`regenerable:` overloads two meanings** (docker-pull-cheap vs days-of-reindexing); `restore.verified` is non-null on **1 of 34** rows.
- **The dump plane's own coupling**: every fast-volume tenant's dump DEST is `/volume4/Backups-Sensitive/…`, on the one bulk pool the doctrine does not yet cover (64 D3 amendment, `opc:F35`).
- **Ephemeral vs durable intent race**: `service stop` writes live `enabled: false` while git declares `true`, and `apply-instance` writes the declaration set as a *replace set* — *"the window's own step 1 re-enabled them and step 5 would start them, into a 7-day resync, with pre-rename binds."* Fixed by `shed[]` at 0.5.15 plus `guard_enable_change`, but `nas.enabled-drift` is still a specified, unregistered check.
